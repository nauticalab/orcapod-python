## `src/orcapod/core/nodes/function_node.py`

### JR1 — After a run, a function job node returned rows of other runs' inputs
**Status:** resolved
**Severity:** high
**Issue:** ITL-1093

A `FunctionJobNode` kept one in-memory cache of results keyed by base entry id, and every read
(`iter_data`, and through it `as_table`, `run()` and any consumer; `head`) returned all of it.
Nothing recorded which inputs the run processed. `async_execute` loads every pipeline record
stored under the node's content hash into that cache before routing its inputs, so after an
async run the node returned every row ever stored for it: partial groups of an earlier run next
to full ones, rows of source rows no longer present. The sync `execute` loaded only its inputs'
entries, so it looked right with a new job per run, but a cache is add-only: running the same
node objects again (one job, its source rebound) accumulated rows on the sync path too. Rows sent
downstream during the run and the `RunSummary` were right on both paths.

**Fix:** The node records the base entry ids of its last completed run's inputs
(`_run_entry_counts`, set by `execute` and `async_execute`), and every read of its rows goes
through one helper, `_held_pairs`, which keeps only those inputs' rows (one per input, so two
equal inputs give two rows, as downstream received them). The cache stays a superset: stored
results of other inputs stay stored and reusable. A run that raised defines no rows: the node
clears its in-memory rows and reads as a node with no run in this process (every row stored
under its content hash), on both orchestrators. Nothing stored, no hash and no layout changed.
A read with no completed run in this process (a fresh or loaded job) still returns every row
stored under the node's content hash.
