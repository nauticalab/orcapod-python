## `src/orcapod/core/nodes/function_node.py`

### CR1 — A job node read without a run showed every stored row, not the current run
**Status:** in progress
**Severity:** high
**Issue:** ITL-1095

A job node is read through the same methods whether or not it has run in this process. After
a run it held the rows of that run's inputs (ITL-1093), but read without one it fell back to the
store: a `FunctionJobNode` hot-loaded every record stored under its content hash (the results of
every earlier run over the same `source_id`, including inputs no longer in the source), a loaded
job's function nodes did the same, and an `OperatorJobNode` in `CacheMode.REPLAY` returned every
logged run. Which view a read gave depended on whether a run had happened in the process, and
nothing said so. A fresh or cleared node also reported `is_stale == False`, and staleness looked
one level up only, so a source rebound two nodes up left the nodes below it "current".

**Fix:** (developer, November 13, 2026) a job node shows its current run and `node.as_source()`
shows everything stored. Function and operator job nodes read empty (typed zero rows, `head()`
`not_computed` pointing to `run()` and `as_source()`) until a run in this process, after
`clear_cache()`, after a run that raised and while stale; no read touches the database. A never-run
or cleared node has no modified time (stale); `core/nodes/staleness.py` makes a job node stale
when any function or operator job node above it is; a `SourceJobNode` is modified when bound or
when its bound source is. `job.run(load_only=True)` fills the nodes from what is stored and
computes and writes nothing. A job node's `run(*, load_only=False)` is state-driven: a current
node runs nothing; otherwise its non-current dependencies run first, once each, on the sync
orchestrator restricted to them (`pipeline/node_run.py`), and the run commits as `job.run()`
does; a failed end-of-run commit clears every node of the run. A load-only run's rows have
status `loaded_only` and are never current for a full run.
