## `src/orcapod/core/nodes/function_node.py` — Rows read back from a function node's database

### FN1 — A result row read back from the database got a fresh datagram id instead of its stored `__data_id`
**Status:** resolved
**Severity:** low
**Issue:** ITL-1060

`FunctionNode._load_cached_entries` built the rows it reads back (sync `iter_data`, the async
cache-only path, a loaded node) from a stream over the stored table with the `__data_id`
column dropped, so each `Data` took a fresh uuid7 on first use. The row's own source-info
token still named the stored id. The result cache lookup (`CachedFunctionPod`, a node's
computed rows) already passes the stored id and was correct.

No stored value could differ because of it: `datagram_uuid` is read only on the OUTPUT of
`process_data` (the pipeline record's `__data_id`, the result record id, the post-run hook
payload), never on an input or a read-back row, and a source-info token is built from the new
output's own uuid at compute time. It was an in-memory identity defect.

**Fix:** `_stored_rows_stream` also returns the stored `__data_id` of each row, and
`_load_cached_entries` rebuilds each `Data` with it as its `datagram_uuid` (same columns,
types, source info and context). Reading the same stored row twice gives the same id. The
operator node cache and `DerivedSource` store no `__data_id`, so there is no stored id to
carry. No hash, record id, golden value or stored table changes.
