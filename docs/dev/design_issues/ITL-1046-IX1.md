## `src/orcapod/core/operators/index.py` — Index and Pick provenance tokens

### IX1 — Index after Batch or GroupBy wrote the text of a whole token list plus `[i]`
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1046

After `Batch` or `GroupBy` the source-info token of a column is a list, one token per member.
`Index` built the element's token as `f"{old_src}[{i}]"`, which for a list is the Python text
of the whole list followed by the index (`"['src::x=1::x', 'src::x=2::x'][0]"`). No resolver
can parse it.

**Fix:** when the incoming token is a list, `Index` takes the element's own token
(`old_src[i]`, negative indices as in Python), one list level removed at every depth: a
column aggregated twice gives the inner list. A scalar token keeps the `<token>[i]` form.
The token's Arrow type follows `arrow_utils.source_info_arrow_type` (`large_string` after one
aggregation, `large_list<large_string>` after two); zero-row and non-empty results agree, as do
the sync and async paths. No hash, record id or golden value depends on the token (a `Data`
content hash excludes source info; the pipeline hash is schema-only). `Pick` is not affected:
its column is a `dict`, which no aggregation produces. Stored tables written with the old text
keep it; upgrading them is the migration tool's job (ITL-1048).
