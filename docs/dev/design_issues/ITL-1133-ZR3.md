## Cross-cutting

### ZR3 — An operator node kept and stored two column orders
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1133

Found during ITL-1131 (ZR2). A job run keeps and stores an operator node's rows in row order
(`_materialize_to_stream`: user tags, system tags, data, source info), but a node run on its
own (`OperatorJobNode.run()`, `_compute_and_store`) kept its operator's result and stored it in
the operator's own order (a join lists its data before its system tags; every operator that
keeps its input's order did the same over a source, which lists system tags after data). So one
node had two populated orders, its table before a run (row order) matched only one of them, and
a database holding rows of both refused the second append (`OrcapodDatabaseWriteError`, schema mismatch, in
the in-memory store and in a Delta database with a pending batch). Only the operator cache
(`odb_v1`) was affected: function pipeline and result tables, side-effect logs and cached
sources store one order on every path. `odb_v1` dates from 2026-11-12 (ITL-967) and was never
released.

**Fix:** every way a node runs its operator keeps `StaticOutputOperatorPod._kept_output` (the
rows as `_materialize_to_stream` builds them, or the zero-row result in row order), so a node
run on its own keeps and stores the row order. The one operator-cache read path
(`OperatorJobNode._read_current_context_records`) puts the user columns of a stored table in
row order (`_in_row_order_on_read`; bookkeeping columns stay in place), so a table an earlier
build stored in the operator's order reads like any other and accepts row-order appends
(developer, November 14, 2026: option B, no layout bump). Record ids do not depend on column
order, so no hash moves. Reproduction: `docs/dev/scripts/itl_1133_store_column_order.py`.
