## `src/orcapod/core/operators/static_output_pod.py` — operator stream staleness

### OS1 — A pass-through operator stream judged its own fresh result stale
**Status:** resolved
**Severity:** high
**Issue:** ITL-1083

An operator with nothing to do returns its input stream itself, unread: a select of every tag
or data column, a drop or rename of absent columns (`DropTagColumns`, `DropDataColumns` with
`strict=False`, `MapTags`, `MapData`), a `PolarsFilter` with no predicate, a `Join` of one
stream, a `SemiJoin` with no common key (its right input is never read). `DynamicPodStream`
stamped `_cached_time` right after `static_process`, before that input had computed. Reading
the kept stream then made the input (a pod stream, or another operator stream) complete its
first computation and stamp a newer modified time, so the next check
(`_update_cache_status`) dropped the operator stream's fresh result: `head()` said "not
computed" with no rows right after `as_table()`, and the next read ran the operator again. A
pod stream reading such an operator stream over a pod stream saw its input move during its
read, was stale after a full read, and called its function again on every row of the next read.
Operators that read their input in `static_process` (`MergeJoin`, `Batch`, `GroupBy`,
`DropNulls`, `Index`, `Pick`, `SelectColumns`, `DropColumns`, and the operators above when they have work to do) stamp after
the input computed and were not affected.

**Rule** (the one F19 / ITL-1065 set for a pod stream's input): an upstream that completes its
first computation after the operator stream kept its result is not a change.

**Fix:** `DynamicPodStream` notes each upstream's state before the operator reads its inputs
(`_upstream_state`), so a change made during that read is seen by the next check: the reset
generation of a pod stream (plus one when that stream is stale,
so a reset its next read makes is counted) or of an operator stream (a new counter, bumped
whenever it discards a kept result), and the modified time of any other upstream. The kept
result is discarded when a state differs or the operator, or an upstream told by time, is newer
or has no modified time. `is_stale` is judged the same way, not by modified-time order. In-memory
bookkeeping only: no hash, saved file or stored table changes. Regressions:
`tests/test_core/streams/test_pass_through_operator_staleness.py` (nine pass-through operators
over a pod stream, a cached pod stream, an operator stream, a pod chain and an operator chain,
read with `as_table`, `iter_data` and `flow`; a pod stream over each operator; a real reset
after the read, directly and two links up, still reruns the operator with the new values; an
upstream reset while a reading operator (`DropNulls`, `Join`) reads leaves it stale).
