## `src/orcapod/core/nodes/function_node.py`

### NV1 — Job node view: a run's rows lost to an observer, failed runs left current, a misleading summary
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1121

A full review of the job node current-run view (ITL-1095) found five defects, each reproduced
through the public interface (`docs/dev/scripts/itl_1121/`):

- A function job node was stamped as modified after `on_node_end`, so an observer reading the
  node there found it stale and cleared the run's rows; the node read empty after the run (sync,
  async and both load-only paths).
- An operator job node without a database, or in `CacheMode.OFF`, computed its lazy output while
  building the `run()` view, outside the block that clears a failed run: after a failure it
  claimed a current run and its reads raised.
- `RunSummary` said "nothing to do; every node holds a current run" when the run ran only a
  side-effect node (which delivered) or an operator node below a held function node: the
  headline judged only the function nodes' counts.
- A side-effect job node's sync `execute(load_only=True)` whose input raised kept its modified
  time, so it and the nodes below it were not stale.
- A load-only run read a side-effect pod's stream outside a job (directly, through another
  stream outside a job, or bound to a source slot), which delivered every row, although a
  load-only run delivers nothing; it also read a function pod's stream outside a job, which
  computed.
- An operator job node without a database did not record a load-only run as one.
- A standalone side-effect job node interrupted while committing its invocation log kept a
  current run, so the next run neither ran nor committed.

**Fix:** stamp before `on_node_end`; build the computed view inside the clearing block;
`RunSummary(ran_nothing=...)` from the run plan; clear the node when the load-only input
raises; the run plan and a source slot's `run()` refuse (`ValueError`, before reading) a
load-only run that would read a `SideEffectPodStream` or a `FunctionPodStream`
(`node_run.refuse_unloadable_inputs`, walking streams outside a job and bound source slots;
developer, November 14, 2026: "Refuse is consistent"); the no-database operator branch
records `load_only`; the side-effect node's log commit clears the node on any interruption. Two review comments did not
reproduce or are tracked elsewhere: a node run outside `job.run()` commits every row, so no
pre-run flush is needed; a function node with no database holding no rows after an async run is
ITL-1097.
