## `src/orcapod/core/function_pod.py`

### F16 — Docs said a function pod extracts the columns it needs; the code rejected any extra column
**Status:** resolved
**Severity:** medium
**Issue:** ITL-807

`docs/concepts/function-pods.md` once said that a function pod picks the columns it needs out
of a wider stream, while `_FunctionPodBase._validate_input_schema` rejected every data column
that was not a parameter of the function. Users had to put a `SelectDataColumns` in front of
each pod by hand (ITL-193 asked for the automatic drop). `__call__` was a plain alias of
`process`.

**Fix:** Developer decision of November 12, 2026. `_FunctionPodBase.__call__(*streams,
label=None, strict=False)` is the convenient call: it joins the inputs as `process` does and,
when the joined stream carries data columns that are not parameters, applies one
`SelectDataColumns(columns=<parameters present>)` after the automatic join and before the
pod, then calls `process`. The select is an ordinary operator step, so the graph, hashes and
stored tables equal those of a pipeline with the select written by hand (the stream methods
`select_data_columns` and `join` build the same operators; pinned by a test); when nothing would
be dropped no step is added. One info message names the dropped columns. `strict=True` and
`process` reject an extra column as before; `strict` is in no identity. No select is added for
a data function whose `accepts_arbitrary_keywords` is true (none today). Operators and
`SideEffectPod` keep `__call__` as an alias of `process`.
