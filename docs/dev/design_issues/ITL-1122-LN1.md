## Cross-cutting

### LN1 — Large normalization applied unevenly across sources and operators
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1122

The rule (developer, November 14, 2026, replacing an earlier form with exceptions for a user's
Arrow table and for a database that keeps the distinction): every column of every table Orcapod
presents or stores has its string, binary and list types in their large variants, with no
exception. Measured on `main` 3a7f3850: `ArrowTableSource` and an explicit Arrow schema kept
`string`; `CSVSource` gave `string` (a CSV file keeps no distinction); `CachedSource` gave the
types its cache store kept (`string` from an in-memory cache, `large_string` from Delta and with
no rows); on a plain stream, the operators that pass rows through (select, drop, map, a filter
with nothing to filter, `Join`, `SemiJoin`, `GroupBy`'s key) kept a source's `string` while every
operator inside a job gave `large_string`, and `Join` of a `string` and a `large_string` input on
a shared tag took the type of whichever input came first in canonical order. No shipped source
store (CSV, Delta Lake, SQLite, PostgreSQL, SpiralDB) keeps the distinction.

**Fix:** one place, `ArrowTableStream.__init__`, normalizes the table every source and every
operator result becomes a stream from (`arrow_utils.normalize_table_to_large_types(...,
keep_null=True)`). Swept by `tests/test_core/operators/test_large_normalization.py` and
`tests/test_core/sources/test_large_normalization_sources.py` (every source kind x operator x
plain / job sync / job async x populated / zero-row).
