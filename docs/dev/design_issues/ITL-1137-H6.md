## `src/orcapod/hashing/semantic_hashing/`

### H6 — A user class hashed before registration hashed by its name only
**Status:** resolved
**Severity:** high
**Issue:** ITL-1137

`TypeObjectHandler` only looked a class up in the logical type registry. A user class (an
ordinary dataclass, an `orcapod.dataclass`, a pydantic model, also nested or inside `list[...]`
or `T | None`) gets its logical type when something registers it: a function pod naming it, a
source built from its values. Before that, the class hashed as `type:<module>.<qualname>`, with
no kind and no fields, so two different classes of one qualified name hashed alike, and the same
schema hashed differently before and after registration. A `Schema` nested in an identity
structure (a node's `(tag_schema, data_schema)`) is expanded as a mapping and never reaches
`SchemaHandler`, so nothing registered the class first; a `Schema` hashed on its own raised
`TypeError` instead. A pipeline hash taken before registration (a job looked at before its
source exists, a slot followed only by operators or by pods that never name the class) was
memoized, so one node wrote function pipeline tables (`pdb_v2`) and operator caches (`odb_v1`)
at two paths depending on what the process built first.

**Fix:** `TypeObjectHandler` resolves the type through
`type_converter.get_logical_type_for_python_type`, which registers a class a factory covers, and
`SchemaHandler` hashes each field type before its translatability check. A registered class
hashes exactly as before and no golden value moves; a class no factory covers still hashes as
`type:<module>.<qualname>`. Tests: `tests/test_hashing/test_type_hash_registration.py`.
