## `src/orcapod/pipeline/job.py` — reading a loaded `PipelineJob`

### LJ1 — a saved job loses column nullability, and does not record the run content hash of an operator node
**Status:** resolved (cache mode not saved remains ITL-977)
**Severity:** high
**Issue:** ITL-1043

Found November 12, 2026. Evidence and scripts: `superpowers/specs/itl-1043/FINDINGS.md`.

- `serialize_schema` (`src/orcapod/pipeline/serialization.py`) writes each column as the Arrow
  type of its Python type. An Arrow `DataType` has no field nullability, so `int | None` and
  `int` are both saved as `"int64"` (nested nullability survives in the type text; only the
  top level is lost). A loaded job's source nodes therefore have non-null schemas, a
  different pipeline hash from the run's, and every loaded node's `output_schema()` drops
  `| None`. An operator node rebuilt with its operator recomputed its pipeline hash from them
  and looked for its cache under another table path; `Pipeline.load` followed by
  `PipelineJob.from_pipeline(sources=...)` still does, so REPLAY reads no rows there and a
  LOG run writes a second table under the wrong path.
- `PipelineJob.save` records the run content hash of function nodes only
  (`run.node_job_content_hashes`). A loaded operator node over in-memory sources (not saved)
  cannot reproduce the content hash its rows are stored under, so it cannot select them.
- The operator's `cache_mode` is not saved (ITL-977).

The running node's hashes are the intended ones: nullability is part of the schema hash
(`docs/reference/hashing.md`; golden `v1/datagram-01.json` `arrow_source.int64` against
`arrow_source.int64_nullable`, `v1/schema-01.json` `multi_field.nullable_type`). No live hash,
stored path or golden value is wrong; only what a loaded job reconstructs.

**Fix:** (ITL-1043; developer decision, November 12, 2026: record the information in the
saved file.) A node descriptor's `output_schema`, a source node's `source_config` and a
source's identity config record `"nullable": {"tag": [...], "data": [...]}`, restored as
`T | None` through the type converter's own rule (`serialization.serialize_nullability`,
`deserialize_output_schema`, `deserialize_schema(nullable=...)`). `PipelineJob.save`
records the run content hash of operator nodes in `run.node_job_content_hashes`; a loaded
operator node returns it, and the pipeline hash saved in its descriptor. The database is the
source of truth (developer, November 12, 2026): a loaded REPLAY node that knows its key
reads as the node built from code does, so no rows under its key (no table, or none of its
rows) is an empty result. A node whose file lacks the run content hash cannot name its
rows: with none under the hash it computes, `as_table()`/`iter_data()` raise and `head()`
shows no rows with the reason. A file without the records (`0.1.0`, or a `0.2.0` file
written before them) loads as before, lossy, and saving it again records nothing it did
not have. No hash, stored path or golden value of a running job changes. Facts about
stored data stay out of the definition: the job file holds only an optional, advisory
`run.expected_rows` section (rows under each node's run key at save time, written only
when certain); a loaded node returns what the database holds and issues one
`OrcapodDatabaseContentWarning` when the number differs. A loaded function node no longer raises on
a database without its run's results (the ITL-904 `node_has_stored_records` flag is no longer
written or read).
