## `src/orcapod/side_effects.py`

### SE2 — Reading a side-effect job node after `job.run()` delivered every side effect again
**Status:** resolved
**Severity:** high
**Issue:** ITL-1091

`SideEffectJobNode` inherited `SideEffectNode.iter_data`, the standalone path: every row was
delivered with no invocation log lookup and no log write. `as_table()`, the dataframe methods,
`flow()`, `async_iter_data()`, `run()` and a downstream node's `run()` went through it, so
reading the node after `job.run()` delivered every side effect again, even with
`track_completion=True`. The node kept nothing after `execute` / `async_execute`; its rows
lived only in the orchestrator's buffers.

**Fix:** The node holds the rows its last completed run passed on (`_held_rows`, set by
`execute` and `async_execute`, cleared when a run starts, so a run that raises leaves none)
and stamps itself modified. `iter_data` and `head` return them while the node is not stale
(`is_stale`, as `FunctionJobNode`) and nothing otherwise; no read delivers. `run()` calls
`execute(self._input_stream)`: the work `job.run()` does for the node, through the log, and
commits the log before it returns, as a job run does. No
stored table, column or hash changed. The blueprint `SideEffectNode` and the standalone
`SideEffectPodStream` are unchanged.
