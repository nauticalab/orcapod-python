## `src/orcapod/core/operators/semijoin.py` — nested columns and string/large_string keys

### SJ3 — `SemiJoin` matched on shared data columns
**Status:** resolved
**Severity:** high
**Issue:** ITL-1088

`SemiJoin` took every name its inputs share, tag or data, as a match key. A shared data column
`y` filtered the left rows by data value, and a name that was a tag on one side and a data column
on the other was matched across the two roles. The operator therefore read data content,
which only filters may do, and a shared data column of another type or nullability made the
graph fail to build.

**Fix:** developer decision, November 13, 2026: "Semijoin should key on shared tags only". The
keys come from one helper, `SemiJoin._match_keys(left_tag_keys, right_tag_keys)`, used by
validation, `binary_static_process` and `async_execute`: the names that are tag columns of both
inputs. Every other shared name is ignored (by name only), and the sync path reads only the
right input's key columns. With no shared tag every left row is returned, as before. Ignored
names raise `SemiJoinIgnoredColumnWarning` (from `_ignored_shared_names`) once per operator and
set of names. The developer considered making them an error and settled, for v0.3, on the
warning, because a stream semi-joined with a filtered copy of itself shares every data name;
the final behaviour is to be decided after use. Developer's note for that decision: once
referential tags are available, the suggestion should be to promote the data column to a tag
on both sides so that it is matched. The identity is unchanged; a cached node in `REPLAY`
serves its stored (old) rows until a `LOG` run stores the new result. Tests in
`tests/test_core/operators/test_semijoin_tag_keys.py`; the nested-key tests in
`test_semijoin_nested.py` now use a shared tag key.
