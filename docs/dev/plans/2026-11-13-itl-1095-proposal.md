# ITL-1095 proposal (sent to the coordinator for decisions)

Measurements: `2026-11-13-itl-1095-node-current-run-view.md` section 1 (same folder).
Recommendations are marked **(rec)**. Decisions needed: D1 to D11.

## A. The rule as built, per node kind

| Node | Before a run in this process (every read) | After a run |
|---|---|---|
| `FunctionJobNode` (FULL; the only state a built job has) | zero rows, typed columns; `head`/preview status `not_computed`, note below | the run's rows (#378); a load-only run: the loaded rows |
| same, after a run that raised / `clear_cache()` / stale (upstream re-ran or was rebound) | empty, as before a run (today: every stored row) | - |
| loaded function node (`READ_ONLY` stub) | empty (today: every stored row) | after `loaded.run(load_only=True)`: loaded rows |
| `CACHE_ONLY`, `READ_ONLY` with a proxy pod (only via `from_descriptor(..., function_pod=...)`, no public path) | empty | D9 |
| `OperatorJobNode` OFF / LOG | empty (unchanged: already so) | run's output (unchanged) |
| `OperatorJobNode` REPLAY | empty (today: union of every logged run) | D1 |
| loaded operator node | empty, no raise (today OFF raises `RuntimeError`) | after a load-only run: its output on the loaded rows |
| `SideEffectJobNode` | #377 (not touched): reads deliver nothing and return zero rows when nothing is held. Already fits the rule. | #377 |
| `SourceJobNode` | the bound source's rows, before and after (a source is not computed); unbound raises as today. **Yes, unchanged.** | same |

`node.as_source()` unchanged: every stored record of the node (current data context).

Head/preview note before a run (D10) **(rec)**: status `not_computed`, header like
`FunctionJobNode[rowwise] — not run; run() fills it, run(load_only=True) loads stored results only; node.as_source() shows every stored result`.
The stored count is NOT available without reading rows (the database protocol has no count; today's
head reads the whole stored slice to show stored rows). Exception: a loaded job whose file records
`expected_rows` for the node: "the saved run stored N rows". **(rec)** no count otherwise, and
`ViewStatus.NOTHING_STORED` then has no producer: remove it (greenfield) **(rec)**, or keep.

## B. Load-only run: `job.run(*, load_only=False)`, `job.run_async(*, load_only=False)`, `node.run(*, load_only=False)`

Keyword-only, default False.

- Sources are read.
- Function node: computes each input's entry id, looks up the node's OWN stored entries (pipeline
  records under its content hash, the lookup a run does today), forwards only the rows it loaded,
  skips and counts inputs without one. No user function call, no side effect, no write to result
  or pipeline tables. An entry whose result was ephemeral and is gone counts as not stored.
  - **D2**: an input with no pipeline record for this node but a matching result in the
    function's result store (same function in another node, or a source renamed with the same
    rows; a normal run "reuses" it and writes a pipeline record). (a) skip it, count it as not
    stored **(rec)**: what the node shows is then always a subset of `as_source()`. (b) show it
    without writing a record.
- Operator node, **D3**: (a) OFF and LOG run their operator on the rows that reach them (cheap,
  not stored; LOG writes nothing in a load-only run), REPLAY replays as in a normal run
  **(rec)**; (b) only cached operators produce rows: OFF (the only mode a job sets) forwards
  nothing, so everything below any operator is empty: load-only becomes useless for
  `group_by`, `join`, `select` pipelines.
  - GroupBy hazard under (a): if the function node above lost inputs (not stored), the groups are
    PARTIAL; a partial group's input differs from the full group's, so the function below misses
    -- unless an earlier, smaller run stored exactly that partial group. Measured case: store has
    the 3-row run, source now 6 rows, `rowwise` stored for 3 of 6 -> load-only groups 3 rows ->
    `summed` HITS the 3-row run's totals (0,22),(1,11) and shows them as this run's. Options:
    (i) the summary marks every node downstream of a node with skipped inputs as "inputs
    incomplete (rowwise skipped 3)" and the docs say so **(rec for the tag)**; (ii) a node below
    a node with skipped inputs forwards nothing (strict; also blanks row-wise chains, which are
    exact); (iii) nothing.
- Side-effect node (D4): **(rec)** the orchestrator passes its input rows through without calling
  it (no delivery, no log write; no change to `side_effects.py`, which #377 owns); the node then
  holds nothing and reads empty. After #377 merges it could hold the passed rows instead.
  A ctx_arg function node is a function node: loads, calls nothing.
- Both orchestrators: same per-node behaviour; `load_only` passed through `run`/`run_async` to
  `execute`/`async_execute`.
- (d) `error_policy`: nothing to apply it to (no function runs); store read errors and
  `TypeIdentityError` raise as in any run, operator errors raise as today. Observers:
  `on_run_start/end`, `on_node_start/end` per node; a loaded row gets `on_data_start` +
  `on_data_end(cached=True)`; a skipped input fires no row hook (no observer protocol change;
  the node counts it and the job reads the count). A user-supplied status/logging observer writes
  its own observability rows as in any run (not result/pipeline tables) -- say if load-only should
  suppress them.
- **D5 RunSummary shape (rec)**: `NodeRunSummary` gains `not_stored: int = 0` (inputs skipped
  because no result is stored, load-only only) and `inputs_incomplete: tuple[str, ...] = ()`
  (upstream nodes that skipped inputs, D3(i)); loaded rows count in the existing `reused` ("read
  from the store"), `computed` and `failed` are 0; `rows` = computed + reused + failed +
  not_stored; `RunSummary.load_only: bool`. Repr line:
  `rowwise: 6 rows: 3 loaded, 3 not stored (skipped)` and
  `summed: 2 rows: 2 loaded (inputs incomplete: rowwise)`. Alternative: a separate `loaded` field.
  Summary nodes stay function nodes only, as today.
- (f) Hashes: none move (no identity, path or record-id change). A load-only run writes nothing:
  tests snapshot every table path and row count of the store before and after, both
  orchestrators, including the operator cache in LOG and a side-effect log.

## C. `node.run()` cascade (developer's rule)

- Today (measured): `node.run()` never runs upstream. With an un-run upstream function node it
  reads the upstream's STORED rows (6, though the source has 3 now) and processes them; over an
  empty store, or behind an un-run OFF operator, it processes nothing and returns 0 rows silently.
- **(rec)** `node.run(*, load_only=False)` runs the sub-graph of the job nodes it depends on plus
  itself, in dependency order, each once (diamonds), with ONE mechanism shared with `job.run`: an
  internal function that takes a node DAG and runs it on the `SyncPipelineOrchestrator`
  (`job.run` passes its whole DAG; `node.run` the ancestor DAG found by walking `upstreams`,
  which in a job are the job nodes). Same rows, stored records, error_policy ("continue") and
  per-node counts as `job.run` for that sub-graph. Sources are read, not run.
- **D7 "not necessarily trigger upstreams"** **(rec)**: an ancestor that holds a CURRENT run is
  not run again; its held rows feed its successors. Current = it holds a completed run in this
  process and `is_stale` is False (the existing judgement: own `last_modified` set and no upstream
  or producer modified later; a re-run or rebound upstream makes it stale) and, for a full
  cascade, that run was not load-only. So after a load-only fill, a full `node.run()` re-runs
  every load-only-filled ancestor in full first (computes their missing entries) **(rec,
  matches your expectation)**; option (b): use the loaded rows as they are. A load-only cascade
  accepts a fully-run ancestor as current (its rows are all stored).
- Side-effect ancestors: a full cascade delivers exactly as `job.run` (with `track_completion`
  only the undelivered); a load-only cascade delivers nothing (passes rows through). An ancestor
  side-effect node that holds a current run (#377) is not run again, so nothing is re-delivered.
- Counts: `node.run()` still returns the node's `StreamView`. **(rec)** the cascade's
  `RunSummary` is kept on the node as `node.last_run` (mirrors `job.last_run`), and a cascade
  with failed rows issues the same `RowFailuresWarning` as `job.run`. Option: attach it to the
  returned view (`view.run_summary`).
- Commits: as a node run on its own does today (every row) plus a flush at the end. Option: the
  job's `commit_every_rows=100` cadence.
- **D6 conflict with a standing rule**: CLAUDE.md (ITL-1081, developer) "Every stream, source and
  node has `run()` with no arguments ... Never give `run()` arguments", enforced by
  `tests/test_core/streams/test_run.py::test_every_stream_class_has_run_without_arguments`.
  **(rec)** amend to: "`run()` takes no positional arguments; a job node's `run()` takes one
  keyword-only argument, `load_only`" and narrow the test to that. Option: `load_only` on
  `job.run` only, and `node.run_load_only()`... (not recommended).

## D. Loaded jobs (`PipelineJob.load`)

- Every loaded node is empty before a run (function stubs and operators alike; operators no
  longer raise from a read). `node.as_source()` reads everything stored (measured: loaded
  `rowwise.as_source()` = 6 rows), with or without sources.
- `loaded.run(load_only=True)` **(rec)**: allowed. Sources come from the file (CSV, Delta) or
  `loaded.bind(sources=...)` (in-memory sources are not saved). Nodes below an unbound source are
  excluded and stay empty, as in any partial run. A function stub can do a load-only run: entry
  ids need no function pod (system tags + input data hash), and the stub reads through its stored
  paths and the saved run's content hash. Operators are rebuilt from the blueprint and run.
  Without any live source there are no inputs to look up: a load-only run is impossible below
  that source, and `as_source()` is the only way in.
- `loaded.run()` without `load_only`, and a loaded `node.run()`: raise as today, message pointing
  to `run(load_only=True)` and `as_source()`. Loaded `node.run(load_only=True)`: the cascade.
- D8: confirm (rec) above. Risk: the stub's lookups use the saved run's content hash; a bound
  source with another `source_id` finds nothing (all inputs counted not stored).

## E. Other load statuses (D9)

`CACHE_ONLY` (no upstream) and `READ_ONLY` with a proxy pod are reachable only through
`FunctionJobNode.from_descriptor(..., function_pod=...)` (tests only). Today their `run()` returns
every stored row. **(rec)** both empty before a run; `READ_ONLY` proxy: `run(load_only=True)`
loads, `run()` raises (cannot compute); `CACHE_ONLY`: no input, so `run(load_only=True)` raises
pointing to `as_source()`. (Candidates for removal later; out of scope.)

## F. REPLAY (D1, not decided by me)

Measured: after a run over 3 rows a REPLAY node holds the union of every LOG run (4 groups, two
from a 6-row run) and feeds it downstream. The rule forces only the BEFORE-a-run part (empty).
Options: (R1) REPLAY after a run keeps meaning "the stored output instead of computing": the
union of every logged run under its content hash; only the before-run read changes **(minimal
for the tag)**. (R2) REPLAY replays only the latest logged run: `odb_v1` stores no run id or time,
so this needs a new stored column -> layout change (`odb_v2`), not for the tag. (R3) REPLAY
replays only the logged rows of THIS run's inputs: operator outputs have no input entry ids, so
not possible without a stored-schema change either.
