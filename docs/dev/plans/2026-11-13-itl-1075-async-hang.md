# ITL-1075 Async job run hangs (bounded-channel deadlock) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use sensei:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An async `PipelineJob.run()` never deadlocks when one node feeds both inputs of a later
`SemiJoin` (or an operator node in `CacheMode.REPLAY` has upstreams), on any run and any `buffer_size`.

**Architecture:** The deadlock is a consumer that stops reading one input while it waits for
something only that input's producer can unblock. On `main` two consumers do that:
`SemiJoin.async_execute` (collects the right input before reading the left) and
`OperatorNode.async_execute` in `REPLAY` (never reads its inputs). Fix each in place: `SemiJoin`
reads the left input while a task collects the right; a `REPLAY` node drains (discards) its
inputs while it replays. No orchestrator, channel or `buffer_size` change.

**Tech Stack:** asyncio, pytest (`asyncio.run(asyncio.wait_for(job.run_async(...)))` as the guard).

Branch: `eywalker/itl-1075-async-job-run-hangs-on-a-re-run-when-one` from `origin/main` `163e5ddc`.

## Cause (established, evidence in the coordinator message)

Task dump of the hung run 2 (1000 rows, buffer 64), each task and the queue it waits on:

- `SJ` (SemiJoin) `collect` of its right input, `get` on edge A -> SJ (0/64): waits for A to close.
- `A` `route_inputs`, `put` on edge A -> J (64/64): the broadcast writer delivers to J's queue first.
- `J` drain tasks `put` on Join's merged queue (64/64); Join loop `put` on J's intermediate (64/64);
  J forward `put` on edge J -> C (64/64).
- `C` `route_inputs`, `put` on edge C -> SJ (64/64): SJ reads its left input only after the right closed.

Cycle: SJ waits A, A waits J, J waits C, C waits SJ.

Run 1 passes because a computing function node runs its pod's `async_execute`, which (no
`max_concurrency`) spawns one task per input row with no limit: C absorbs every row J emits,
so J never blocks. Proof: capping `max_concurrency` at 4 makes run 1 hang the same way. On a
cache-hit run `route_inputs` sends hits straight to the output with a blocking send.

300 rows pass at buffer 64 because the cycle's queues hold about 3 x buffer + 130 rows
(A -> J, J -> C, C -> SJ at `buffer_size`, plus Join's merged queue and the operator node's
intermediate channel at a fixed 64) before anything blocks.

### Task 2: SemiJoin reads both inputs at once

**Files:** Modify `src/orcapod/core/operators/semijoin.py` (`async_execute`)

> **Superseded** by "CodeRabbit review round" below: this loop stays blocked in
> `left_ch.receive()` when the right input ends meanwhile. The shipped code awaits each left
> receive as a task together with the right task, and hands a receive still pending to the
> left rows (`_LeftRows`). The example is kept as the original plan.

```python
async with asyncio.TaskGroup() as tg:
    right_task = tg.create_task(right_ch.collect())
    early_left = []
    left_closed = False
    while not right_task.done():
        try:
            early_left.append(await left_ch.receive())
        except ChannelClosed:
            left_closed = True
            break
right_rows = right_task.result()

async def left_rows():
    for row in early_left:
        yield row
    if not left_closed:
        async for row in left_ch:
            yield row
```

The rest of the method iterates `left_rows()` where it iterated `left_ch`. Output order stays
the left arrival order. Memory: left rows that arrive before the right input closes are held
(at most the whole left input, as the barrier `MergeJoin` holds both inputs and the sync path
holds both tables); after that the left streams with backpressure.

## CodeRabbit review round (review 5900648222 of `f8dd3163`, 2026-11-14)

Findings: one inline Major (`semijoin.py` ~351), and two LanguageTool notes in the review body.

- Major: `_collect_right_reading_left` checks `right_task.done()` only before awaiting
  `left.receive()`. Reproduced (scratch script): with one matching left row sent and the left
  channel open, right closed, SemiJoin emits nothing until the left sends again or closes; a
  `right.collect()` that raises surfaces only after the left closes. No pipeline deadlock is
  reachable with today's consumers (every consumer reads all of its inputs at once), so the effect
  is delayed probing and a delayed right error. Fix:
  - wait on the pending left receive (a task) and `right_task` together
    (`asyncio.wait(..., FIRST_COMPLETED)`); a finished receive's row is kept (or `ChannelClosed`
    ends the left); when `right_task` is done, stop;
  - never cancel the pending receive on the success path: the left iterator yields the kept rows,
    then awaits the pending receive, then reads the rest, so the left arrival order is kept;
  - on a failure (right raises, cancellation, a probe error) the pending receive is cancelled:
    the run is failing and the left rows are discarded anyway;
  - tests (event-controlled, `asyncio.wait_for` only as a hang guard, no sleeps) in
    `tests/test_channels/test_native_async_operators.py`: matching row emitted while left open;
    right-side error raised while left open.
