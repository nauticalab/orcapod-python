# Orcapod Python v0.2.0 — release checklist (ITL-810)

Prepared 2026-11-09 against `main` at `61d0f18e`; updated 2026-11-10 after every selected
v0.2 PR merged (`main` at `c5ab1e05`). This is the ordered list of steps to cut `orcapod`
0.2.0, followed by the ITL-810 cut checklist with the evidence for each item.

Nothing here has been triggered. The Release workflow has not been run and no tag has been
created. Every PR selected for 0.2.0 is merged except this one (#269), including the MIT
license (#283, ITL-875) and the golden hash regression suite (#284, ITL-626). **This PR
merged is the last precondition of the cut.**

**Developer decisions since this checklist was first written (2026-11-09):**

- **Distribution reversed (2026-11-10).** Orcapod is MIT licensed starting with 0.2.0, is
  published on public PyPI as `orcapod`, and the repository `metamorphic-labs/orcapod-python`
  will become public (ITL-875). This replaces the 2026-11-09 decisions (private
  repository, proprietary license, internal registry only), which are void. The license
  files change in #283; `.github/workflows/release.yml` is not changed.
- **0.2.0 is tag-only (developer, 2026-11-10).** Nothing is published for 0.2.0: the
  coordinator creates the `v0.2.0` tag on the release commit after this PR merges, and
  0.3.0 is the first release published to PyPI from this repository. The public release
  route (trusted publishers, rehearsal; ITL-875) is prepared for 0.3.0.
- Python 3.13 is supported (ITL-825, #275). It landed on `main` through #276.
- The organization's required CI (`ruff`, `ruff format`, `basedpyright`, `pytest` on Python
  3.11, 3.12 and 3.13) is met by ITL-826 (#276, merged 2026-11-10 as `7dec4b54`, which
  also contains #275).
- Operator outputs keep their inputs' Arrow types, normalized to large variants:
  `MergeJoin` (with zero-row inputs), `PolarsFilter`, `Batch` and `GroupBy` (ITL-813 and
  ITL-832, #278, merged 2026-11-10 as `ab544982`; #268 was closed as superseded by it),
  and `Index` / `Pick` (ITL-834, #279, merged 2026-11-10 as `fde06d20`). Both change some
  row content hashes and have entries under *Breaking changes and migration*.
- ITL-837, ITL-845 and ITL-849 were added to 0.2.0 on 2026-11-10 and merged the same day
  (#280, #282, #281). Type strictness applies everywhere: no implicit widening; disagreeing
  Arrow types are an error naming the column and both types.
- ITL-604 (#248, `NodeConfig.missing_cache_policy`) moves to v0.3.
- The golden hash regression suite (ITL-626, #284) is part of 0.2.0 (developer,
  2026-11-10). Hash values must stay identical across releases.

  def f(age: int) -> int:

### 7. Trigger the workflow — only if every box in step 6 is ticked (not run for 0.2.0: tag-only)

Do not create the tag by hand on this path: the `build` job creates and pushes it.

**Keep `main` at the commit you checked in step 4 until `build` has pushed the tag.** The
workflow builds whatever `main` is when its jobs check it out, not the commit you checked.
Before triggering, confirm `git ls-remote origin refs/heads/main` prints that commit, and
merge nothing until `build` finishes. If `main` moves before the tag is pushed, cancel the
run and repeat step 4 on the new commit. If the tag was pushed on a different commit, cancel
the run and wait until it has finished. Then check
<https://pypi.org/project/orcapod/#history>, <https://test.pypi.org/project/orcapod/#history>
and the logs of `publish-testpypi` and `publish-pypi`. Only if neither index has `0.2.0`
and neither job uploaded anything, delete the tag (`git push origin :refs/tags/v0.2.0`) as
in "If a Run Fails Part-Way" in `RELEASING.md` and start again. If anything was published,
or you cannot tell whether an upload happened, the version is used: keep the tag.

[Actions → Release → Run workflow](https://github.com/metamorphic-labs/orcapod-python/actions/workflows/release.yml)

| Input | Value |
|---|---|
| Use workflow from | `main` |
| Version | `0.2.0` |
| Branch | `main` (the default) |

What the run does, job by job (`.github/workflows/release.yml`):

1. `validate-branch` checks that the branch exists on origin.
2. `test (3.11)`, `test (3.12)`, `test (3.13)` (`uv sync --locked --all-extras --dev`, then
   `pytest -m "not postgres"`) and `license-check` run in parallel.
3. `build` strips a leading `v`, creates the local tag `v0.2.0`, runs `uv build`, aborts if
   the tag already exists on origin, pushes the tag, and uploads `dist/` as an artifact.
4. `publish-testpypi` (environment `testpypi`) runs
   `uv publish --publish-url https://test.pypi.org/legacy/ dist/*`, authenticating through
   OIDC trusted publishing (`id-token: write`).
5. `publish-pypi` (environment `pypi`), after TestPyPI succeeds, runs `uv publish dist/*`
   the same way, then creates the GitHub Release for `v0.2.0` with generated notes and the
   dist files attached.
6. `linear-sync` runs after `build`, in parallel with publishing; `linear-complete` runs after
   `publish-pypi` and `linear-sync` succeed.

If the `testpypi` / `pypi` environments have required reviewers, approve the deployment
when the run pauses.

**If a job fails**, follow "If a Run Fails Part-Way" in `RELEASING.md`. In short:
- **Before the tag is pushed:** fix the problem and start a new run.
- **`build` fails after the tag push** (for example in *Upload dist artifact*): do not use
  **Re-run failed jobs**, because a rerun of `build` stops at *Guard against duplicate tag*.
  Confirm that nothing was published (neither index has `0.2.0` and no publish job ran),
  delete the unused tag (`git push origin :refs/tags/v0.2.0`), and start a new run.
- **A publish job fails:** use **Re-run failed jobs** on the same run.

A release candidate is not recommended here. Everything up to the tag push fails safely,
TestPyPI stages the upload, and an `rc` run would also publish the candidate to PyPI and run
`linear-complete`, closing the Linear release early.

## Findings to decide on

None of these was changed in this PR. Findings 1–4 are addressed by ITL-827 (#277,
merged 2026-11-10); finding 1 again by #283.

1. **There is no `LICENSE` file.** `pyproject.toml` declares MIT, but neither the
   repository nor the wheel contains the licence text. *Decided 2026-11-09:* proprietary;
   #277 added the `LICENSE` file and declared `LicenseRef-Metamorphic-Proprietary`.
   *Reversed 2026-11-10:* MIT from 0.2.0; #283 (ITL-875) replaces the text and declares
   `license = "MIT"`.
2. **The sdist publishes internal material.** It contains `superpowers/` (183 files of
   agent plans and specs), `tests/`, `CLAUDE.md`, `DESIGN_ISSUES.md`, `plan.md`,
   `notebooks/` and more — 3.3 MB against a 0.6 MB wheel. Earlier releases did the same.
   #277 limits the sdist to the package source and its metadata files.
3. **`basedpyright` is a runtime dependency.** A type checker is installed for every
   user. #277 moves it (and `typing_extensions`) to the `dev` group and removes the
   unused `pymongo` and `pyyaml`.
4. **`orcapod.__version__` does not exist**, although `orcapod/_version.py` is generated.
   #277 adds it.
5. **`v0.1.4` points at a commit on no branch.** `origin/patch` stops at `v0.1.3`.
6. **`CLAUDE.md` and `.zed/rules` still say "greenfield project pre-v0.1.0"** as the
   reason not to keep backward compatibility. After 0.2.0 ships with a migration tool,
   that policy deserves a deliberate restatement.
7. **`linear-sync` and `linear-complete` check out the default branch**, not the
   `branch` input. Harmless for a release from `main`; wrong for a hotfix release.
