## `src/orcapod/core/datagrams/tag_data.py`

### DG2 — A dropped data column kept its source info, so async runs stored an extra column
**Status:** resolved
**Severity:** high
**Issue:** ITL-1040

`Data` did not override `Datagram.drop` or `Datagram.select`, so both left the removed
columns' entries in `Data._source_info`. The source-info table that `as_table(source=True)`
and `arrow_schema(source=True)` use was built from all of `_source_info`, while `as_dict` and
`source_info()` filtered it to the current columns.

The async paths of `SelectDataColumns` and `DropDataColumns` drop columns one datagram at a
time with `data.drop`. Their sync paths drop the `_source_` columns from the table
explicitly. So an async run stored an extra `_source_<dropped column>` in the function node's
pipeline records that a sync run did not, and the stored table's schema depended on the
orchestrator. This happened after the automatic select in front of a pod, and after any
explicit select or drop. On one store, mixing orchestrators then either widened a Delta table
(with nulls) or failed an in-memory commit with a schema mismatch. The cell values were always
the row's own. The row-alignment suite found it (ITL-1034). It had been reported for `Data` alone as ITL-838.

**Fix:** `Data.drop` and `Data.select` remove the source info of the columns they remove, and
the source-info table holds only the entries of current columns. Sync and async runs now
store identical records (`tests/test_pipeline/test_sync_async_stored_records.py`). No hash,
record id or stored path depends on source-info columns.

A Delta table that an async run wrote before the fix keeps its extra column. Rows written
after the fix have null in it, which is what a sync run appending to such a table already did
before the fix. No migration in this release; migrating stores written by earlier versions is the job of the migration tool planned after v0.3 (ITL-1048).
