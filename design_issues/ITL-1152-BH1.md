## `src/orcapod/hashing/semantic_hashing/builtin_handlers.py` — bytes and UUID value hashes (ITL-1152)

### BH1 — A bytes value hashed as the string of its hex digits; a UUID as its bytes
**Status:** resolved
**Severity:** high
**Issue:** ITL-1152 (with ITL-1154)

`BytesHandler` hashed a `bytes` or `bytearray` value as `obj.hex()`, so a bare bytes value had
the same semantic hash as the string of its hex digits (`hash_object(b"hello") ==
hash_object("68656c6c6f")`, and `b""` equalled `""`). `UUIDHandler` returned the UUID's 16
bytes, which then went through `BytesHandler`, so a UUID, its bytes and its 32-digit hex text
shared one hash. A type confusion in an identity hash, found by the ITL-946 worker on
November 15, 2026. UUID columns were also routed through the value handler, although their
16 stored bytes are already their identity.

**Fix:** (ITL-1154, rules 2 and 3) a value handler describes its value as tagged data:
`BytesHandler` returns `Encoded("bytes", {"hex": ...})` and `UUIDHandler` returns
`Encoded("uuid", {"hex": ...})`, hashed by `semantic_v1`. `bytes` and `bytearray` of equal
content still hash equal. `UUIDHandler.COLUMN_VALUE_HANDLER = False`: a UUID column is hashed
as stored by starfix (extension identity plus the bytes), while a bare `uuid.UUID` keeps its
tagged value hash. `tests/test_hashing/test_hash_collisions.py` checks through the public
hasher that bytes, str and UUID never collide, at the top level or nested. The label stays
`semantic_v1`: no release shipped data context `v1`.
