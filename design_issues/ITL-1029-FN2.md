## `src/orcapod/core/nodes/function_node.py`

### FN2 — a job node's sorted table attached content hashes to the wrong rows
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1029

`FunctionNodeBase._shape_table` sorted the rows of a function node's table by tag
(`arrow_utils.apply_column_config` with `sort_by_tags`, which `all_info=True` turns on) and
only then appended the `_content_hash` column, built from `iter_data()` in the order the node
held its rows: input order on the sync path, completion order on the async path. Whenever
that order was not tag order, `node.as_table(all_info=True)` gave rows the content hash of
other rows. On the async path rows finish out of order at random, which made two tests that
compare a script run with a run inside an event loop fail now and then on CI (ITL-1001); on
the sync path an input not in tag order showed it every time. Stored records, record ids and
stored hashes were correct; no library code reads that column.

**Fix:** `_shape_table` selects the column groups, appends the hash column, and only then
sorts (`arrow_utils.sort_by_tag_columns`), as `FunctionPodStream.as_table` and
`ArrowTableStream.as_table` already did. `tests/test_pipeline/test_job_node_row_hashes.py`
forces both orders deterministically (reversed input; an async row held back by an event).
