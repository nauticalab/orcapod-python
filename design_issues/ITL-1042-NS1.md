## `src/orcapod/core/nodes/function_node.py`

### NS1 — After an async run a function node looked stale, so downstream heads said "not computed"
**Status:** resolved
**Severity:** high
**Issue:** ITL-1042

A node is stale when an upstream (or its pod) has a newer modified time than its own. The sync
`FunctionJobNode.execute` stamps the node when its run completes; `async_execute` never did.
An `OperatorJobNode` stamps itself when its async run finishes, so a function node downstream
of an operator node (most often the automatic `SelectDataColumns` that `pod(stream)` adds when
the stream has columns the function does not take, ITL-807) was stale right after an async
run. Its first `iter_data()` / `as_table()` then threw away the in-memory results, re-read the
node's whole stored table (two `get_all_records` calls) and stamped the node. That made every
operator node downstream of it stale, and their `head()` reported `not_computed` ("inputs
changed since the last computation") with no rows, although `as_table()` and `iter_data()`
still returned every row. `head()` of the function node itself read the store instead of
memory. No function was called again and no operator recomputed.

**Rule:** a job node stamps its modified time once per completed run, after it has read all
its inputs and before it closes its output, on both paths; a failed run does not stamp. Every
node then ends a run at least as new as its upstreams, so nothing is stale after a completed
run, and `head()`, `as_table()` and `iter_data()` serve the run's results from memory. The
same rule governs function pod streams outside a job (F18, ITL-1052).

**Fix:** `async_execute` stamps the node after its run completes and before its `finally`
closes the output. On the no-database path the pod closes the writer it is given, so it gets a
writer whose close is left to the node. No hash, stored value or public API changes.
Regressions: `tests/test_pipeline/test_node_staleness_after_run.py` (sync and async, a forced
reverse completion order, in-memory and Delta stores; staleness, heads, store reads, function
calls, a second run).

Not changed: a `SideEffectJobNode` never stamps, on either path, so it reads as stale after a
run; it keeps no rows and nothing reads its staleness. A head with no rows still shows the
declared columns only (no `_source_*`, `_context_key` or content-hash column; decision of
November 12, 2026, recorded on ITL-985 and ITL-1002).
