## `src/orcapod/core/operators/group_by.py` — tags entering the data group (ITL-955)

### GB2 — `GroupBy` kept non-key tags as list-valued tags
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1070

GB1 (ITL-955) stopped `GroupBy` from moving non-key tags into the data group by keeping them as
list-valued tags. A list of the members' values is not a key for the group, though, and a
grouped non-key tag that falls through a function pod is stored on every result row: in the
referential workshop pipeline it was the remaining cost (77 MB against 11 MB of store).

The rule (developer, November 13, 2026): `GroupBy` keeps only its `by` tags; a tag that is not
a key is dropped, as SQL drops a non-key, non-aggregated column after `GROUP BY`. Data columns
are unchanged. `Batch` keeps its list-valued tags: it has no key. An opt-in mode that keeps
non-key tags as lists is ITL-1071.

**Fix:** the output's tag columns are the `by` columns, scalar, in the input's tag order;
`unary_output_schema` predicts the same. The dropped tags still order the members, so every
data list, system-tag fold, row data hash and stream hash is unchanged; no golden value moves
(six `pipeline:group_by.row[...]` keys are renamed, because a row's key names its user tags).
Tables written by a development build between ITL-955 and this fix sit at the same paths with
the old tag column: a write to them fails and a read returns the old column; the changelog
tells users to delete them. Nothing checks a stored table's columns against the node's schema
on read; that gap is ITL-1072.
