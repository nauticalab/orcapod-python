## `src/orcapod/core/function_pod.py` — Table assembly of a function pod stream and node

### FP1 — `as_table` built rows and content hashes in two passes: a stale upstream between them gave old rows with new rows' hashes
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1045

`FunctionPodStream.as_table` (and `_CachedFunctionPodStream`, `FunctionNodeBase.as_table`, the
same structure) used its cached table without a staleness check, then built the content hashes
in a second `iter_data()` pass. `iter_data()` clears a stale cache. So when the upstream was
reset between `as_table()` and `as_table(columns={"content_hash": True})` (a non-deterministic
function, `clear_cache()` on the upstream), the old cached rows got the hashes of the new rows,
and no row's `_content_hash` was the hash of its own data.

**Fix:** `as_table` clears a stale cache first, before any of it is used, so the table and the
hashes come from the same rows and the call returns the current rows. For a job node no
public sequence changes the values between the two passes (its results come from the store),
so the defect was latent there; the same few lines fix its structure. No hash, golden value,
stored table or public API changes.
