## Cross-cutting

### ZR2 — A zero-row table had a different column order from its populated table
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1131

ITL-912 (ZR1) gave every table with no rows the Arrow types and nullability of the rows, but
not always their column order or all their columns. A `Join` or `MergeJoin` job node after a
run whose input had no rows (sync `OperatorJobNode.execute()` and the async empty branch)
kept the operator's own result, which lists data before system tags, while a run with rows
keeps `_materialize_to_stream` (row order: user tags, system tags, data, source info).
`Index` and `Pick` built their empty result from the input's table without system tags
(`Pick` also without source info, so its source-info columns came out nullable, and without
the token of an `out=` column). The row order was restated in two places
(`StaticOutputOperatorPod._zero_row_input`, `OperatorJobNode._typed_zero_row_table`).

**Fix:** the row order has one owner, `StaticOutputOperatorPod._in_row_order`, used by
`_zero_row_input`, `OperatorJobNode._typed_zero_row_table`, `_zero_rows_in_row_order` (what a
node keeps after a sync or async run with no rows) and `_as_row_built_table` (row order plus
source-info flags; `Index` and `Pick` build their empty result from the input with system
tags and source info through it). `tests/test_pipeline/test_zero_row_column_order.py` checks
every operator and a function pod, plain stream and job node, sync and async, before a run
and after a zero-input run, with one and two system-tag pairs. No populated or stored order
changed.

Found alongside it and fixed in the same change: an operator node run on its own kept and
stored its operator's order (ZR3, ITL-1133).
