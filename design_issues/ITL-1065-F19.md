## `src/orcapod/core/function_pod.py`

### F19 — Interleaved reads of a pod stream fed by an operator stream recomputed a yielded row
**Status:** resolved
**Severity:** high
**Issue:** ITL-1065

A regression from F18 (PR #355). With two iterators open on one function pod stream whose
input is an operator stream (for example the automatic `SelectDataColumns` that `pod(src)`
inserts when `src` has a data column the function does not take), the second iterator dropped
the stream's results and computed them again: 7 calls of the function for 6 rows, and the row
the first iterator had already yielded was no longer the stream's row. A read left after one
row and then read again did the same.

**Cause** (modified times printed at each step): the first read found the stream stale (its
input, the operator stream, had no modified time before it ran), so `clear_cache()` stamped
the stream at t1; then opening the input made the operator stream compute and take t2 > t1.
The stream stamps again only when its input is read to the end (F18), so until then it was
older than its input: `last_modified` was `None` and `is_stale` True in the middle of the read,
and the next `iter_data()` cleared it. Before F18 the stream stamped right after opening (and
so computing) the operator input, which hid this. A source is older than the stream, and a
pod-stream input stamps only at its end, so neither showed it directly; a pod stream over an
operator-fed pod stream did.

**Rule:** a pod stream's results are judged in one of two ways.

- Completed results (the input read to the end, or nothing read since a reset) are current
  while neither a direct upstream nor the pod is newer or without a modified time (F18).
- Results in progress (a read has noted its input's state and not reached the input's end) are
  current while that state is unchanged, the input is not stale itself and the pod did not
  change. The state is the reset generation of a pod-stream input, and the modified time of
  any other input, noted when its first row (or its end) arrives. An upstream completing, or
  computing, for the first time during the read is not a change of the stream's input. A
  pod-stream input is also asked whether it is stale, because its generation does not move
  when a stream further up is reset; any other input's modified time already reflects its
  upstreams.
- A read in progress ends when any read reaches the input's end (the stream stamps, or clears
  its modified time if the input changed) or when the stream is reset (`clear_cache()`, also
  the one a stale stream's next read makes). An abandoned iterator does not end it: the
  stream keeps its partial results and its open input, and the next read resumes it
  (ITL-1039) unless the input changed, in which case that read finds the stream stale and
  starts again.

An operator stream needs no reset generation of its own: it computes when it is opened, so by
the time the pod stream notes its modified time it has computed, and that time moves only when
it is invalidated or recomputed, which are real changes.

**Fix:** `FunctionPodStream.is_stale` applies the in-progress rule while a noted input state
exists; `_input_read_to_end` ends the read in progress after stamping (or clearing) the
modified time. A reset upstream during a read still changes the noted state: the next read of
the stream starts again, and the stream ends a read that saw the reset stale (F18 unchanged).
In-memory bookkeeping only: no hash, saved file or store sees it. Regressions:
`tests/test_core/function_pod/test_pod_stream_interleaved_reads.py` (source, operator, pod
stream and pod-over-operator inputs; sequential and concurrent paths; plain and cached pods;
interleaved reads, an abandoned partial read, a reset one or two links up between
interleaved reads or after an abandoned read, `head()` after an abandoned read (partial, not
stale), and `as_table()` or `head()` while an iterator is
open).
